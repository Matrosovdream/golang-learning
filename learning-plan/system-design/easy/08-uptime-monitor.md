## 1. The task

> "Design an uptime monitoring service, a small Pingdom. Customers register URLs; we check them
> every minute from several locations and alert them when a site goes down."

A system whose *writes* are generated by a clock rather than by users. The hard parts are
making a million timers fire on time and not crying wolf.

## 2. Clarifying questions

| Ask | Why it matters | Assumed answer |
|---|---|---|
| How many monitors? Check intervals? | Checks per second. | 1M monitors; intervals 30 s to 5 min, average 1 min. |
| What is a check? | HTTP only, or TCP/DNS/keyword/latency thresholds? | HTTP(S) GET: status code, response time, optional keyword. |
| How many locations? | Multiplies the checks and enables agreement. | 3 regions. |
| When is a site "down"? | One failed request is noise. | Down when ≥ 2 of 3 regions fail twice in a row. |
| Alert channels? Latency to alert? | Integration with task 12. | Email, Slack, webhook; within ~2 minutes of the real outage. |
| History and retention? | Time-series volume. | 90 days of history, uptime % and response-time charts. |
| Public status pages? | Read path for the public. | Yes, per customer. |
| Multi-tenancy? Limits? | Per-customer quotas. | Plans cap monitors and minimum interval. |

## 3. Requirements

**Functional**
- CRUD monitors (URL, interval, expected status, keyword, regions).
- Run each check on schedule from each configured region; record status, latency, error.
- Decide UP/DOWN with multi-region confirmation; alert on transitions (down and recovered).
- Show history: uptime %, response-time charts; public status page.

**Non-functional**
- Checks run within a few seconds of their scheduled time; no monitor is silently skipped.
- Alerts within 2 minutes of a real outage, with few false positives.
- The monitor itself is more available than what it monitors.

**Out of scope**
- Synthetic multi-step browser tests, incident management workflow, SLA contracts.

## 4. Back-of-the-envelope

| Quantity | Estimate | How |
|---|---|---|
| Checks per second | ~16.7k/s per region → **50k/s total** | 1M monitors ÷ 60 s × 3 regions |
| Concurrent in-flight checks per region | ~17k × ~0.5 s avg = ~8k; worst case with 10 s timeouts: 170k | rate × duration |
| Result records per day | 4.3B | 50k × 86,400 |
| Raw result size | ~100 B → **~430 GB/day** | timestamp, monitor, region, status, latency, error code |
| 90 days raw | ~39 TB | too much; store raw 7 days, 1-min aggregates 90 days |
| 1-min aggregates | 1M monitors × 1,440/day × ~50 B = 72 GB/day | still large; roll to 1-hour after 7 days |

What the numbers tell us: this is a **throughput** problem in two places: firing 50k timers a
second on schedule, and ingesting 50k result rows a second. Storage must be time-series shaped
with downsampling or it is 40 TB of rows nobody reads.

## 5. Plan

1. Scheduling: how 1M monitors become 16.7k due checks per second, reliably, with several scheduler nodes.
2. Execution: worker pools with timeouts and bounded concurrency per region.
3. Aggregation: turning per-region results into a single UP/DOWN with hysteresis.
4. Alerting: once per transition, with recovery.
5. Storage: raw vs aggregates, retention, the status page read path.
6. The monitor monitoring itself.

## 6. High-level design

```
 customer ──► API ──► Postgres (monitors, customers, alert rules)
                        │ on create/update: ZADD due:{region} next_run_at monitor_id   (per region)
                        ▼
 ┌─ region eu ───────────────────────────────────────────────────────────────────┐
 │ scheduler (×2, leader or SKIP-LOCKED style) ── every 1 s: pop due ids ──► queue │
 │ checkers (pool, ~2k goroutines each) ◄── queue ── HTTP GET with 10 s timeout    │
 │          └──► results stream (Kafka / NATS)                                      │
 └─────────────────────────────────────────────────────────────────────────────────┘
      ⋮ same in us, ap
 results stream ──► aggregator: per monitor, latest result per region ──► state machine
                       │  UP→DOWN when ≥2 regions fail 2× in a row; DOWN→UP when ≥2 pass
                       ├──► alerts → notification service (task 12)
                       └──► time-series store (raw 7 d, 1-min rollups 90 d)
 status page / dashboards ──► API ──► rollups (cached, CDN for public pages)
```

Every second each region's scheduler pops the monitors due now from a sorted set keyed by
`next_run_at`, pushes them to a queue, and re-adds them with `next_run_at + interval`. Checkers
consume the queue, perform the HTTP request with a hard timeout, and emit a result. The
aggregator keeps the last few results per monitor per region and runs the UP/DOWN state machine.

## 7. API

```
POST   /monitors        { "url": "https://…", "interval_s": 60, "regions": ["eu","us","ap"],
                          "expect_status": 200, "keyword"?: "OK", "timeout_s": 10 }  → 201
GET    /monitors/{id}   → config + current state + last check per region
PATCH  /monitors/{id}   → 200 (reschedules)
DELETE /monitors/{id}   → 204

GET /monitors/{id}/checks?from=…&to=…&resolution=1m     → series of (ts, status, p50/p95 latency, failures)
GET /monitors/{id}/uptime?period=30d                     → { "uptime_pct": 99.93, "incidents": [...] }

POST /monitors/{id}/alert-channels   { "type": "slack", "target": "…" }
GET  /status/{customer-slug}         public status page (cached)
```

## 8. Data model

```sql
CREATE TABLE monitors (
    id             BIGINT PRIMARY KEY,
    customer_id    BIGINT NOT NULL,
    url            TEXT NOT NULL,
    interval_s     INTEGER NOT NULL CHECK (interval_s BETWEEN 30 AND 3600),
    timeout_s      INTEGER NOT NULL DEFAULT 10,
    regions        TEXT[] NOT NULL,
    expect_status  INTEGER NOT NULL DEFAULT 200,
    keyword        TEXT,
    state          TEXT NOT NULL DEFAULT 'unknown',   -- up | down | unknown | paused
    state_since    TIMESTAMPTZ,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE incidents (
    id          BIGINT PRIMARY KEY,
    monitor_id  BIGINT NOT NULL REFERENCES monitors(id),
    started_at  TIMESTAMPTZ NOT NULL,
    ended_at    TIMESTAMPTZ,
    cause       TEXT                                 -- "timeout", "status 503", "keyword missing"
);

-- time-series (TimescaleDB hypertable / ClickHouse table / partitioned-by-day Postgres)
CREATE TABLE check_results (
    ts          TIMESTAMPTZ NOT NULL,
    monitor_id  BIGINT NOT NULL,
    region      TEXT NOT NULL,
    ok          BOOLEAN NOT NULL,
    status      SMALLINT,
    latency_ms  INTEGER,
    err         SMALLINT                             -- enum code, not text
);  -- partition by day; drop partitions older than 7 days

CREATE TABLE check_rollups_1m (
    bucket      TIMESTAMPTZ NOT NULL,
    monitor_id  BIGINT NOT NULL,
    region      TEXT NOT NULL,
    checks      INTEGER, failures INTEGER,
    p50_ms      INTEGER, p95_ms INTEGER,
    PRIMARY KEY (monitor_id, region, bucket)
);
```

Redis (per region): `due:{region}` sorted set, score = `next_run_at` (unix seconds), member = `monitor_id`.

## 9. Deep dives

### 9.1 Scheduling a million timers

The question is "which monitors are due *now*", 16.7k answers per second per region, from
several scheduler nodes without double-firing.

| Approach | How | Pros | Cons |
|---|---|---|---|
| a goroutine/timer per monitor | `time.AfterFunc` × 1M | trivial code | 1M timers in one process; no failover; restarts lose the schedule |
| **DB polling** | `SELECT id FROM monitors WHERE next_run_at <= now() FOR UPDATE SKIP LOCKED LIMIT 1000` | durable, multi-node safe via `SKIP LOCKED` (task 15) | 17k row updates/s per region just to bump `next_run_at`; the index on `next_run_at` churns |
| **Redis sorted set as a due-queue** | `ZRANGEBYSCORE due 0 now LIMIT 1000` then `ZADD` with the next time, in one Lua script | O(log N) per pop, 17k/s is easy; multiple schedulers safe because the script is atomic | Redis holds the schedule: rebuild it from Postgres on loss (1M `ZADD`, seconds) |
| **Partition ownership** | each scheduler owns `monitor_id % P` partitions (lease in etcd) and keeps an in-memory timing wheel | no shared store on the hot path; scales linearly | rebalancing on node changes; more moving parts |

**Choice: Redis sorted set per region**, with the pop-and-reschedule in one Lua script so two
scheduler nodes never pop the same monitor. Postgres remains the source of the schedule
(interval, regions) and rebuilds the set after a loss. Partition ownership is the next step at
10× (medium: distributed task queue).

**Jitter.** If 100k monitors are created by an import at 12:00:00 with a 60 s interval, they are
all due together every minute: a spike for us *and* for the checked sites. Add a random offset
within the interval on creation so due times spread evenly: `next_run_at = now + rand(0, interval)`.

**Drift.** Reschedule relative to the *scheduled* time (`due + interval`), not the actual run
time, or slow checks push every subsequent check later.

### 9.2 Running checks

- A pool of checker goroutines per region reads the queue; each check has a **hard timeout**
  (`context.WithTimeout`, 10 s) covering DNS, connect, TLS and the first byte. A site that hangs
  must cost exactly one timeout, not a stuck worker.
- **Bounded concurrency:** at 17k checks/s with 0.5 s typical latency, ~8k are in flight; with
  timeouts, more. A semaphore of ~20k per region, backpressure from the queue if exceeded.
- Don't download the body: `GET` with a small read limit (keyword checks read the first 64 KB), then close.
- **DNS caching** with a short TTL; otherwise 17k DNS queries/s.
- **Follow redirects?** Up to N, record the final status. Refuse to connect to private IP ranges
  (customers must not use us to scan their internal networks; same SSRF logic as task 10).
- Be a polite client: `User-Agent` that identifies the service, no more than the configured rate per target host.

### 9.3 From results to a verdict

A single failed request from one region is usually *our* problem (a flaky route) or noise. The
aggregator keeps, per monitor, the last two results per region and runs a state machine:

```
 UP ──(≥2 regions failed their last 2 checks)──► DOWN      → open incident, alert "down"
 DOWN ──(≥2 regions passed their last check)──► UP          → close incident, alert "recovered"
 any ──(no results for 3 intervals)──► UNKNOWN              → alert *us*, not the customer
```

- **Confirmation** (2 consecutive failures) trades alert latency for precision: at a 60 s interval,
  detection is 1–2 minutes, within the agreed 2 minutes.
- **Quorum across regions** (2 of 3) filters regional network problems.
- **Hysteresis:** going DOWN needs two failures, coming UP needs one success per region; a site
  flapping around the threshold produces few transitions. Add a minimum DOWN duration before
  recovery is announced if flapping still generates noise.
- The verdict runs where all regions' results meet: a central aggregator consuming the results
  stream, partitioned by `monitor_id` so one monitor's results are processed in order by one consumer.

### 9.4 Alerting

Alerts fire on **transitions**, not on every failed check. The aggregator writes the incident
row and enqueues one notification per channel to task 12's service, with an idempotency key
`incident:{id}:down`. Recovery sends `incident:{id}:up`. Escalation (re-notify after 30 minutes
still down) is a scheduled job (task 15) keyed on the open incident.

### 9.5 Storing 50k results a second

| Layer | Resolution | Retention | Size |
|---|---|---|---|
| raw results | every check | 7 days | ~3 TB |
| 1-minute rollups | per monitor, region, minute | 90 days | ~6 TB (compressed far less) |
| 1-hour rollups | per monitor, hour | 2 years | small |

- Insert raw results in **batches** (1,000 rows per `COPY`/multi-row insert) from the aggregator;
  single-row inserts at 50k/s would be the bottleneck.
- A columnar or time-series store (ClickHouse, TimescaleDB) compresses these rows 10–20× and makes
  "p95 latency over 30 days" a cheap aggregate. Plain Postgres partitioned by day works to start;
  drop old partitions instead of `DELETE`.
- Rollups are computed continuously (a minute behind) so the dashboards and status pages read only
  rollups. Uptime % for 30 days is a sum of two integers per bucket.
- Public status pages: rendered JSON cached for 30–60 s, served through the CDN.

### 9.6 Who monitors the monitor

If the scheduler stops, no checks run, no failures are recorded, and every site looks UP. That is
the worst failure mode. Defences: a **dead man's switch** (the scheduler pings an external
heartbeat service every minute; silence alerts us), metrics on `checks_scheduled` vs
`checks_completed` per region, the UNKNOWN state above, and running the alerting path in a
different region from the one being checked.

## 10. Scaling, bottlenecks & failure modes

- **What breaks first at 10×:** the single Redis due-queue per region at 170k pops/s and the
  results ingestion at 500k rows/s. Shard the due-queue by `monitor_id` (several sorted sets, each
  owned by a scheduler) and partition the results stream; the time-series store scales by adding nodes.
- **A region goes dark:** its checks stop; the quorum rule still works with 2 of the remaining 2;
  the UNKNOWN rule alerts us. Never let one region's outage become a flood of DOWN alerts.
- **Redis due-queue lost:** rebuild from Postgres (`next_run_at = now + rand(interval)`); checks
  resume within a minute with a one-off spread.
- **A customer's site is slow (10 s timeouts) at scale:** bounded per-host concurrency keeps it from
  consuming the pool; its checks cost one timeout each, nothing more.
- **Results stream lag:** verdicts are late, alerts are late. Monitor consumer lag; it's the key SLO metric.
- **Noisy neighbour:** a customer with 100k monitors at 30 s. Plan limits and per-customer rate caps (task 03).

## 11. Trade-offs at a glance

| We chose | Instead of | We gain | We give up |
|---|---|---|---|
| Redis sorted-set due-queue | DB polling | 17k pops/s cheaply, multi-scheduler safe | the schedule must be rebuilt from Postgres after loss |
| quorum + 2 consecutive failures | alert on first failure | few false alerts | 1–2 minutes of detection latency |
| alerts on transitions | alert per failed check | one alert per incident | must maintain state per monitor |
| raw 7 d + rollups 90 d | raw everything | 10× less storage, fast dashboards | raw detail older than a week is gone |
| batched inserts, columnar store | row inserts in Postgres | 50k rows/s ingest | another database to run |

## 12. Check yourself

1. Why not a `time.Ticker` goroutine per monitor in one scheduler process?
2. Two scheduler nodes in a region: how do you make sure a monitor isn't checked twice per interval?
3. What problem does jitter solve, and when do you apply it?
4. A regional network blip fails 30k checks at once. What do customers receive, and why?
5. All monitors read UP for an hour. Name two signals that would tell you something is wrong with *you*.

<details><summary>Answers</summary>

1. A million timers in one process with no failover: a restart loses the schedule and a crash stops
   all checks; you also can't add a second scheduler for load. A shared, durable due-queue keeps the
   schedule outside any one process and lets several nodes pop from it.
2. Make the pop-and-reschedule atomic: one Lua script that reads the due members and immediately
   `ZADD`s them with `next_run_at + interval`. A second node's script runs after the first and
   sees them no longer due. With `SKIP LOCKED` in Postgres the same guarantee comes from row locks.
3. Synchronised due times: many monitors created at the same time with the same interval would fire
   together every cycle, spiking our load and hammering target hosts. Apply a random offset within the
   interval when a monitor is created or rescheduled after a rebuild.
4. Nothing. The verdict requires at least two regions to fail two consecutive checks; one region's
   30k failures are a single-region, single-cycle event and don't cross the threshold. We should get
   an internal alert about the region's failure rate instead.
5. A dead man's switch that stops receiving the scheduler's heartbeat; a gap between
   `checks_scheduled` and `checks_completed`; monitors transitioning to UNKNOWN because no results
   arrived; results-stream consumer lag; a sudden drop in the results ingest rate.

</details>
