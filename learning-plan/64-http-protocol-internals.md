# 64 — The HTTP Protocol & `net/http` Internals (HTTP/1.1 → 2 → 3, TLS)

> Part of **Part 14 — Networking & Serving**, the second lesson: [63 — TCP/IP & sockets](63-networking-fundamentals.md) → **64 the HTTP protocol & the machine that implements it** → [65 — Container & Docker networking](65-docker-networking.md) → [66 — Every way to serve a Go app](66-serving-go-apps.md). This is the **theory under [20 — HTTP Server](20-http-server.md) and [21 — REST API](21-rest-api.md)**: what actually travels over the socket from [63](63-networking-fundamentals.md), and what `http.Server`/`http.Transport` do with it. Thesis: **HTTP is a text (then binary) framing convention on top of a TCP byte stream, and `net/http` is a modest amount of code around an accept loop. Once you can write an HTTP request by hand and describe the server's goroutine-per-connection loop, timeouts, connection pooling, keep-alive, and proxy headers stop being magic.**

## Goals
- Read and write **HTTP/1.1 on the wire** by hand: request line, headers, `CRLF CRLF`, body — and know how the receiver finds the **end of the body** (`Content-Length` vs `chunked`).
- Explain **keep-alive**, head-of-line blocking, and what **HTTP/2** (binary frames, multiplexed streams, HPACK) and **HTTP/3** (QUIC over UDP) change — and what Go gives you automatically.
- Understand **TLS**: the handshake, certificate chains, **SNI**, **ALPN** (how h2 gets negotiated), and where termination happens.
- Trace `net/http` **server internals**: `ListenAndServe` → `Serve` loop → `go c.serve()` → parse → `ServeMux` → `ResponseWriter` → `Flusher`/`Hijacker`/`ResponseController`; and configure the **five timeouts**.
- Trace **client internals**: `http.Client` → `http.Transport` **connection pool**, why you must drain+close bodies, and the tuning knobs.
- Work correctly **behind a proxy**: `X-Forwarded-For`/`Proto`, `httputil.ReverseProxy`, and trusting only your own hop.

## Concepts

- **HTTP/1.1 is text you can type.** A request is a **request line** (`GET /users/7 HTTP/1.1`), **headers** (`Name: value`, one per line), a blank line, then an optional body. The response mirrors it: **status line** (`HTTP/1.1 200 OK`), headers, blank line, body. Everything is `CRLF`-terminated. `printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80` is the whole protocol. **`Host` is mandatory** in 1.1 — it's how one IP serves many sites (virtual hosting), the plaintext cousin of TLS **SNI**.
- **Where does the body end?** TCP gives a stream with no boundaries ([63](63-networking-fundamentals.md)), so HTTP must say. Three answers: **`Content-Length: N`** (read exactly N bytes), **`Transfer-Encoding: chunked`** (a sequence of `<hex size>CRLF<bytes>CRLF`, terminated by a `0` chunk — used when the length isn't known up front, i.e. streaming), or **close-delimited** (HTTP/1.0 style: body ends at EOF, which kills reuse). In Go: if you `Write` without setting `Content-Length`, the server buffers a little, and if the handler returns quickly it sets the length for you — otherwise it switches to **chunked** automatically. Streaming (SSE, [58](58-realtime-websockets-sse.md)) is chunked plus `http.Flusher`.
- **Keep-alive and its limits.** HTTP/1.1 connections are **persistent by default**: multiple request/response pairs reuse one TCP+TLS connection, amortizing the handshakes from [63](63-networking-fundamentals.md). But responses must come back **in order** on that connection — **head-of-line blocking**. Pipelining (sending request 2 before response 1) was the 1.1 fix; it's effectively dead. The real fix in practice: browsers open ~6 connections per host, and clients pool them (`http.Transport`).
- **HTTP/2 = the same semantics, a new wire format.** One TCP connection carries many **streams**, each a sequence of **binary frames** (`HEADERS`, `DATA`, `SETTINGS`, `WINDOW_UPDATE`, `RST_STREAM`). Streams **multiplex** — request 3's response can arrive before request 1's, so no application-level HOL blocking. Headers are compressed with **HPACK** (a shared dynamic table — repeated headers cost a byte or two). Per-stream and per-connection **flow control** exists. Notes: it's still **one TCP connection**, so a lost packet stalls *all* streams (transport-level HOL); server push is deprecated/removed in browsers; header names are lowercase.
- **HTTP/3 = HTTP/2's semantics over QUIC over UDP.** **QUIC** puts streams and loss recovery in userspace on top of **UDP** ([63](63-networking-fundamentals.md)), so a lost packet only stalls *its* stream. TLS 1.3 is built into the handshake (1 RTT, or **0-RTT** for resumption), and connections survive an IP change (connection IDs — phone switching Wi-Fi→LTE). Not in the standard library: use **`quic-go`**'s `http3` package ([66](66-serving-go-apps.md)). Requires **UDP** to be open/published — a real deployment gotcha.
- **What Go does for you.** Server: HTTP/2 is enabled automatically for **TLS** servers (via ALPN) when you use `ListenAndServeTLS` with a default `TLSConfig`; cleartext HTTP/2 (**h2c**) needs `x/net/http2/h2c` ([66](66-serving-go-apps.md)). Client: `http.Transport` negotiates h2 over TLS automatically (`ForceAttemptHTTP2`). Your handlers are **version-agnostic** — the same `http.Handler` serves 1.1, 2, and 3; check `r.Proto` if you care.
- **TLS in five steps.** ClientHello (with **SNI** = the hostname, and **ALPN** = the protocol list `h2, http/1.1`) → ServerHello + **certificate chain** → key agreement → *Finished* → encrypted application data. The client verifies the chain up to a trusted **root CA** (the system pool — missing in `scratch` images, see [65](65-docker-networking.md)) and that the cert's **SAN** matches the hostname. In Go this is `crypto/tls`: `tls.Config{MinVersion: tls.VersionTLS12, Certificates: ...}`, `tls.Listen`/`ListenAndServeTLS`; `r.TLS` on the server tells you the negotiated version/cipher/SNI. **mTLS** = the server also demands a client cert (`ClientAuth: RequireAndVerifyClientCert`). Most production Go services never terminate TLS themselves — the load balancer or ingress does ([62](62-deployment-operations.md)).
- **`net/http` server internals — the whole machine.**
  1. `http.ListenAndServe(addr, h)` = `net.Listen("tcp", addr)` + `srv.Serve(ln)`.
  2. `Serve` runs the **accept loop** and starts **one goroutine per connection** (`go c.serve(ctx)`) — exactly the pattern from [63](63-networking-fundamentals.md).
  3. Per connection: read a request with `bufio.Reader` + `textproto` header parsing → build `*http.Request` (with a **context** cancelled when the client disconnects) → call `srv.Handler.ServeHTTP` (defaults to `http.DefaultServeMux` if `nil` — one reason to always pass your own mux).
  4. `ServeMux` matches the pattern (Go 1.22+ method + wildcards, [20](20-http-server.md)), the handler writes through `ResponseWriter` — a buffered writer that **locks headers on the first `Write`/`WriteHeader`** and infers `Content-Type` by sniffing the first 512 bytes.
  5. After the handler returns, the connection is kept alive for the next request (unless `Connection: close`), and any **unread request body is drained** so reuse is possible.
  - The escape hatches: **`http.Flusher`** (push bytes now — SSE), **`http.Hijacker`** (take the raw `net.Conn` — WebSockets, [58](58-realtime-websockets-sse.md)), **`http.ResponseController`** (Go 1.20+: per-request `SetReadDeadline`/`SetWriteDeadline`/`Flush` without type assertions), `http.CloseNotifier` (deprecated — use `r.Context()`).
- **The five server timeouts (set them — the defaults are "none").** `ReadHeaderTimeout` (slow-loris defense — the cheapest big win), `ReadTimeout` (headers+body), `WriteTimeout` (from end of headers to end of response), `IdleTimeout` (how long a keep-alive connection may sit unused), `MaxHeaderBytes`. **Trap:** a global `WriteTimeout` kills SSE/streaming/long downloads — use a generous one plus `ResponseController.SetWriteDeadline` per request, or per-route `http.TimeoutHandler` for the normal endpoints ([57](57-web-security.md), [62](62-deployment-operations.md)).
- **Client internals: the `Transport` is the pool.** `http.Client` is a thin policy layer (timeout, redirects, cookies, jar); **`http.Transport`** does the work: it keys idle connections by `(scheme, host, port, proxy)` and reuses them. The knobs that matter: `MaxIdleConns`, **`MaxIdleConnsPerHost` (default 2 — the classic hidden bottleneck when you hammer one backend)**, `MaxConnsPerHost`, `IdleConnTimeout`, `DialContext` timeouts, `TLSHandshakeTimeout`, `ResponseHeaderTimeout`, `ExpectContinueTimeout`, `DisableCompression` (the Transport adds `Accept-Encoding: gzip` and transparently decodes — unless *you* set the header, in which case you own the decoding). **Create one `Client`/`Transport` and share it**; a per-request Transport leaks connections and defeats pooling.
- **The two client rules that cause 90% of client bugs.** (1) **Always set a timeout** — `http.DefaultClient` has none, so a hung server hangs your goroutine forever; prefer a per-request `context.WithTimeout` + `http.NewRequestWithContext`. (2) **Always `defer resp.Body.Close()`, and drain it** (`io.Copy(io.Discard, resp.Body)`) if you don't read it all — an unread body means the connection **cannot be reused** and the pool grows a new one every call.
- **Status codes, methods & semantics carry contracts.** **Safe** (GET/HEAD/OPTIONS — no side effects) and **idempotent** (+ PUT/DELETE — repeatable) matter because **only idempotent requests may be blindly retried** ([36](36-resilience-patterns.md)); POST needs an **idempotency key** ([41](41-api-design-evolution.md)). `100 Continue`, `206 Partial Content`/`Range` (resumable downloads), `304 Not Modified` with `ETag`/`If-None-Match` (caching, [38](38-caching-patterns.md)), `429`/`Retry-After` (rate limits, [57](57-web-security.md)), `503` during shutdown ([62](62-deployment-operations.md)).
- **Proxies change what your handler sees.** A **forward proxy** sits in front of clients; a **reverse proxy** (nginx/Caddy/Traefik/ALB/ingress) sits in front of *you* ([66](66-serving-go-apps.md)). Behind one, **`r.RemoteAddr` is the proxy's IP**, and the real client is in **`X-Forwarded-For`** (a comma list — take the **rightmost hop you trust**, never blindly the first, which is client-controlled and a spoofing/[57](57-web-security.md) hazard), with `X-Forwarded-Proto`/`X-Forwarded-Host` (or the standard `Forwarded` header) telling you the external scheme/host for redirects and cookie `Secure` flags. Also: proxies may buffer responses (breaking SSE — `X-Accel-Buffering: no`), enforce their own idle timeouts (silent `connection reset`), and rewrite/strip hop-by-hop headers (`Connection`, `Upgrade` — which is why WebSocket needs explicit proxy config).
- **`httputil.ReverseProxy` — a proxy in 10 lines of Go.** `httputil.NewSingleHostReverseProxy(url)` or, since 1.20, `&httputil.ReverseProxy{Rewrite: func(pr *httputil.ProxyRequest){ pr.SetURL(target); pr.SetXForwarded() }}` (`Rewrite` supersedes `Director` and handles the forwarded headers safely). Add `ErrorHandler`, `ModifyResponse`, `FlushInterval` (for streaming) and you have a BFF/API gateway, a canary splitter, or a local dev proxy.

## Exercises
1. Type an HTTP/1.1 request by hand over `nc` (and over `openssl s_client -connect host:443` for TLS); read the raw response including headers.
2. Serve a response with an explicit `Content-Length`, then one that goes **chunked** (stream with `Flusher`) — confirm with `curl -v --raw`.
3. Compare `curl -v --http1.1` vs `--http2` against a TLS Go server; print `r.Proto` in the handler and observe the ALPN result.
4. Configure the **five timeouts** on `http.Server`; prove `ReadHeaderTimeout` kills a slow-loris client (a connection that dribbles headers).
5. Break streaming with `WriteTimeout`, then fix it with `http.ResponseController.SetWriteDeadline`.
6. Write a middleware that logs method, path, status, bytes, and duration — which requires wrapping `ResponseWriter` (and forwarding `Flush`/`Hijack`, or using `ResponseController`).
7. Client side: benchmark 200 requests with a shared `http.Client` vs a new one per request; then set `MaxIdleConnsPerHost` and re-measure. Watch the connection count with `ss -tn`.
8. Prove the drain rule: make 100 requests without closing/draining bodies, count sockets, then fix it and re-count.
9. Serve TLS locally with a self-signed cert (`crypto/tls` + `mkcert` or a generated cert), set `MinVersion: TLS12`, and inspect `r.TLS` (version, cipher, SNI).
10. Build a **reverse proxy** with `httputil.ReverseProxy` + `Rewrite`/`SetXForwarded` in front of two backends; add an `ErrorHandler`, then write the `X-Forwarded-For` parsing that trusts only your proxy hop.
11. Capstone: an **HTTP/1.1 parser by hand** — read the request line + headers from a hijacked `net.Conn`, handle `Content-Length` *and* chunked bodies, and write a valid response. Then run the same handler over HTTP/2 and diff nothing.

## Best Practices & Pitfalls
- **Never use the zero-value `http.Server` or `http.DefaultClient` in production.** No timeouts on either side is the single most common Go availability bug.
- **Never register on `http.DefaultServeMux`** (`http.HandleFunc`) in a real app — any imported package can add routes to it (`net/http/pprof` famously does, exposing profiles publicly).
- **Share one `http.Client`/`Transport`; always drain and close response bodies.** Otherwise you lose pooling and leak sockets.
- **Set headers before `WriteHeader`/`Write`.** After the first write the header map is ignored — a silent no-op that confuses everyone once.
- **Trust `X-Forwarded-For` only from your own proxy.** Client-supplied hops are attacker-controlled; that header drives rate limits, audit logs, and IP allowlists ([57](57-web-security.md)).
- **Pitfall — assuming `r.Body` can be read twice.** It's a one-shot stream; buffer it (`io.ReadAll` + `MaxBytesReader`) if middleware and handler both need it.
- **Pitfall — HTTP/2 over a proxy that only speaks 1.1.** Negotiation is per-hop; `r.Proto` reflects the hop you're talking to, not the browser's.
- **Pitfall — `WriteTimeout` and long responses.** Uploads/downloads/SSE need per-request deadlines, not a global one.
- **Pitfall — retrying non-idempotent requests.** A retried POST can double-charge. Retry GET/PUT/DELETE; use idempotency keys for POST ([35](35-sagas-distributed-transactions.md)/[41](41-api-design-evolution.md)).
- **Prefer `NewRequestWithContext` everywhere** so cancellation and deadlines propagate across hops ([15](15-sync-context.md), [39](39-observability-tracing.md)).
