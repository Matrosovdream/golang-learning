# 63 — Networking Fundamentals: TCP/IP, Sockets & the `net` Package

> Part of **Part 14 — Networking & Serving**, the opener: **63 the wire & sockets** → [64 — HTTP & `net/http` internals](64-http-protocol-internals.md) → [65 — Container & Docker networking](65-docker-networking.md) → [66 — Every way to serve a Go app](66-serving-go-apps.md). This is the layer *underneath* [20 — HTTP Server](20-http-server.md): before `net/http` there is a **socket**, and before a socket there is a **TCP connection**. Pairs with [13](13-goroutines.md)/[15](15-sync-context.md) (the accept loop is a goroutine factory) and [58](58-realtime-websockets-sse.md) (which hijacks the raw connection). Thesis: **`net.Conn` is just a file descriptor with deadlines. Every networking bug you will ever debug — hangs, `connection refused`, half-open connections, "why is my message split in half" — is explained by the four-tuple, the byte stream, and who closes first.**

## Goals
- Place Go's `net` package on the **TCP/IP stack**: link → IP → TCP/UDP → your protocol.
- Understand a **connection** as a 4-tuple, the **3-way handshake**, the **byte stream with no message boundaries**, and the close sequence (`FIN`, `TIME_WAIT`, half-open).
- Map Go calls to syscalls: `net.Listen` → `socket`/`bind`/`listen`, `Accept` → `accept`, and know why **goroutine-per-connection** is cheap (the netpoller).
- Write a raw **TCP server/client** with framing and deadlines, and a **UDP** and **Unix-socket** peer.
- Resolve names correctly (**DNS**, Go's pure-Go vs cgo resolver) and read the errors the network gives you.

## Concepts

- **The stack, in one paragraph.** Your bytes go down four layers: **application** (HTTP, gRPC, Redis — your problem), **transport** (**TCP** = reliable ordered stream, **UDP** = unreliable datagrams — the `net` package's home), **internet** (**IP** — addressing and routing, best-effort), **link** (Ethernet/Wi-Fi frames, **MTU** ≈ 1500 bytes). Each layer wraps the one above in a header. Go's `net` package hands you a transport-layer endpoint and lets the kernel do everything below it.
- **An address is IP + port; a *connection* is four numbers.** A TCP connection is uniquely identified by the **4-tuple** `(src IP, src port, dst IP, dst port)`. That's why *one* listening port can serve 10,000 clients: each accepted connection has a different client port. Ports **0–1023** are privileged (binding needs root or `CAP_NET_BIND_SERVICE`); clients get an **ephemeral** port (Linux ~32768–60999) automatically. `:8080` means "all interfaces" (`0.0.0.0`), `127.0.0.1:8080` means "loopback only — nobody outside this machine (or container, see [65](65-docker-networking.md)) can reach me".
- **TCP: handshake, stream, teardown.**
  - **Open:** `SYN` → `SYN-ACK` → `ACK` (one round trip *before* any data; that's why connection reuse matters — [64](64-http-protocol-internals.md)).
  - **Transfer:** a **byte stream**. TCP guarantees order and delivery, and guarantees **nothing about message boundaries**. One `Write` of 1000 bytes may arrive as three `Read`s; three `Write`s may arrive as one. **Framing is your job**: length-prefix (`binary.Write` a `uint32` then the payload), a delimiter (`bufio.Scanner`, `ReadString('\n')`), or a self-describing format. This is the single most common raw-TCP bug.
  - **Close:** each side sends `FIN` independently — a connection can be **half-open** (peer done writing, still reading). Go surfaces the peer's `FIN` as **`io.EOF`** on `Read`. `CloseWrite()` on a `*net.TCPConn` sends your `FIN` while still reading. The side that closes **first** sits in **`TIME_WAIT`** (2×MSL, ~60s) holding the tuple — thousands of `TIME_WAIT` sockets on a *client* means you're opening a new connection per request instead of reusing.
  - Writing to a connection the peer already reset gives **`ECONNRESET`** / `broken pipe`.
- **Sockets are file descriptors.** `net.Listen` performs `socket()` + `bind()` + `listen(backlog)`; `Accept()` is `accept()`. Every connection is an **open fd**, so `ulimit -n` (`RLIMIT_NOFILE`) is a hard ceiling on concurrent connections — "too many open files" is a leaked-`Close` bug 95% of the time. The kernel keeps an **accept queue** (backlog); if you accept too slowly it fills and new `SYN`s are dropped — the client sees a hang or a refusal.
- **Why goroutine-per-connection is fine in Go.** The classic C choice is thread-per-connection (expensive) or an event loop (`epoll`, awkward). Go gives you both: fds are set **non-blocking** and registered with the **netpoller** (`epoll` on Linux, `kqueue` on BSD/macOS, IOCP on Windows). A blocking `conn.Read` **parks the goroutine** (a few KB of stack) and the runtime resumes it when the poller says data arrived. So the idiomatic accept loop — `for { c, err := ln.Accept(); go handle(c) }` — scales to tens of thousands of connections. `net/http` does exactly this ([64](64-http-protocol-internals.md)).
- **`net.Conn` is the interface that matters.** It is `io.Reader` + `io.Writer` + `io.Closer` + **deadlines**: `SetDeadline`, `SetReadDeadline`, `SetWriteDeadline` (absolute times, not durations; call them **before each** read/write). Deadlines are the *only* way to time-limit a blocked read — there is no "cancel this read". The other lever is `conn.Close()` from another goroutine, which makes the blocked `Read` return an error. A timed-out read returns an error satisfying `net.Error` with `Timeout() == true`; also `errors.Is(err, os.ErrDeadlineExceeded)`.
- **UDP is a different shape.** No handshake, no connection, no ordering, no retransmission — but **message boundaries are preserved**: one `WriteTo` = one datagram = one `ReadFrom`. Use `net.ListenPacket("udp", ":9000")` and `ReadFrom(buf)` (which returns the sender's address) — there's no per-connection goroutine because there are no connections; one reader goroutine + a worker pool. Size the buffer for your largest datagram: **excess bytes are silently discarded**. This is what DNS, QUIC/HTTP-3, and metrics agents (statsd) ride on.
- **Unix domain sockets: same API, no network.** `net.Listen("unix", "/tmp/app.sock")` gives you a `net.Listener` that speaks the exact same interfaces — but stays in the kernel (no TCP/IP, no checksums, lower latency) and is protected by **filesystem permissions** instead of firewall rules. The gotcha: a stale socket file makes `bind` fail with `address already in use` — remove it before listening, and `Close()` the listener on shutdown. Very common between a Go app and a local nginx ([66](66-serving-go-apps.md)).
- **DNS: names → addresses, with a cache.** `net.Dial("tcp", "api.example.com:443")` resolves first: **A**/**AAAA** records (v4/v6), possibly through **CNAME**s, cached for the record's **TTL**. Go has **two resolvers**: the **pure-Go** one (parses `/etc/resolv.conf` itself, non-blocking, works in a `scratch` container) and the **cgo** one (calls `getaddrinfo`, honors `nsswitch.conf`/NSS modules). Selection is automatic and overridable with `GODEBUG=netdns=go` / `netdns=cgo`; `CGO_ENABLED=0` builds ([60](60-build-package.md)) always use pure Go. Use `net.Resolver` with a `Context` to make lookups cancellable, and remember a resolved IP can go stale — long-lived connections don't re-resolve.
- **The middle boxes that break your assumptions.** **NAT** (your container/laptop has a private `10.x`/`172.16-31.x`/`192.168.x` address rewritten on the way out) means inbound connections need explicit mapping ([65](65-docker-networking.md)); NAT/firewall tables **drop idle connections** after minutes, which is why **TCP keepalive** exists (Go's `http.Server` enables it on accepted conns) and why long-lived idle connections die silently. **MTU** mismatches (VPNs, overlay networks at 1450) show up as "the TLS handshake hangs on some networks".
- **Latency and buffers.** Every round trip costs; a TLS 1.3 handshake adds one more on top of TCP's. **Nagle's algorithm** batches small writes — Go disables it by default (`SetNoDelay(true)`) because interactive protocols care more about latency than packet count. Socket buffers (`SetReadBuffer`/`SetWriteBuffer`) plus the receiver's advertised window determine throughput; `Write` returning early is normal — always use `io.Copy`/`io.ReadFull` rather than assuming one call moves everything.
- **Read the errors — they're diagnostic.** `connection refused` = the packet arrived, **nothing is listening** on that port (wrong port, bound to the wrong interface, container not up). `i/o timeout` / silent hang = packets **dropped** (firewall, security group, wrong host, MTU). `no such host` = DNS. `address already in use` = another process holds the port (or a stale unix socket, or `TIME_WAIT` without `SO_REUSEADDR` — Go sets it for you). `EOF` = the peer closed cleanly. `connection reset by peer` = it closed rudely (crash, LB idle timeout, proxy).
- **The debugging toolbox.** `ss -tulpn` / `lsof -i :8080` (who is listening), `nc -vz host port` and `nc -l 9000` (dumb client/server), `curl -v` / `curl --resolve`, `dig +short name` (DNS truth vs your app's view), `ping`/`traceroute` (reachability — note ICMP is often blocked), `tcpdump -i any port 8080 -A` or Wireshark (the actual bytes), and `ss -s` / `netstat -an | grep TIME_WAIT | wc -l` when you suspect connection churn.

## Exercises
1. Talk to a server with `nc` and `telnet`; type an HTTP request by hand and watch the response ([64](64-http-protocol-internals.md) makes this precise).
2. Write a TCP echo server (`net.Listen` + accept loop + `go handle(conn)`) and a `net.Dial` client; check `ss -tnp` while it's connected.
3. Break it on purpose: send a message in two `Write`s and read it with one `Read`. Then fix it twice — once with a `\n` delimiter (`bufio.Scanner`), once with a 4-byte **length prefix** (`binary.Write`/`io.ReadFull`).
4. Add **deadlines**: `SetReadDeadline` per read, an idle timeout that closes the connection, and a graceful shutdown that closes the listener and drains in-flight handlers.
5. Trigger and identify each error by hand: `connection refused`, `i/o timeout`, `no such host`, `address already in use`, `EOF`, `connection reset`.
6. Write a UDP echo pair with `net.ListenPacket`/`ReadFrom`/`WriteTo`; send a datagram larger than your buffer and observe the truncation.
7. Swap the same echo server onto a **Unix domain socket**; handle the stale-socket-file case and set permissions.
8. Use `net.Resolver` with a context to look up A records; compare `GODEBUG=netdns=go` vs `netdns=cgo` (`GODEBUG=netdns=2` prints which is used) and cross-check with `dig`.
9. Measure: time 1000 sequential `Dial`+request+close vs 1000 requests over one connection. Count `TIME_WAIT` sockets after each.
10. Capstone: a small **line-protocol server** (`SET k v` / `GET k`) — accept loop, per-connection goroutine, a mutex-guarded map, read/write deadlines, an idle timeout, connection limit, and graceful shutdown. Load it with 500 concurrent clients.

## Best Practices & Pitfalls
- **Always `defer conn.Close()`** in the handler goroutine, and `Close()` the listener on shutdown. Leaked fds end as `too many open files`.
- **Never assume message boundaries on TCP.** Frame explicitly. If you find yourself calling `conn.Read(buf)` once and parsing `buf`, you have a latent bug.
- **Always set deadlines on raw connections.** A `net.Conn` with no deadline can block a goroutine (and its fd) forever against a dead peer — the classic slow-loris resource leak.
- **Bind to `0.0.0.0` in containers, `127.0.0.1` when a local proxy fronts you.** Getting this backwards is the #1 "works locally, unreachable in Docker" bug ([65](65-docker-networking.md)).
- **Reuse connections.** Dial-per-request burns a handshake *and* leaves `TIME_WAIT` behind; that's exactly what `http.Transport`'s pool prevents ([64](64-http-protocol-internals.md)).
- **Pitfall — ignoring short reads/writes.** `Read` returning `n < len(buf)` is normal, not an error. Use `io.ReadFull`, `io.Copy`, or a `bufio` wrapper.
- **Pitfall — resolving once and caching forever.** In dynamic environments (containers, cloud LBs) the IP behind a name changes; long-lived connections must be re-dialed, and health checks must actually re-resolve.
- **Pitfall — treating `Timeout()` and permanent errors alike.** Retry timeouts (with backoff, [36](36-resilience-patterns.md)); don't retry `connection refused` in a tight loop.
- **Cap concurrency, don't just `go handle(conn)` forever.** A semaphore or `netutil.LimitListener` ([66](66-serving-go-apps.md)) keeps a connection flood from OOM-ing the process.
