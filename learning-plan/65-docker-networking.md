# 65 — Container & Docker Networking for Go Services

> Part of **Part 14 — Networking & Serving**, the third lesson: [63 — TCP/IP & sockets](63-networking-fundamentals.md) → [64 — HTTP & `net/http` internals](64-http-protocol-internals.md) → **65 the same networking, inside containers** → [66 — Every way to serve a Go app](66-serving-go-apps.md). Applies the wire-level model from [63](63-networking-fundamentals.md) to the images built in [60](60-build-package.md) and the deploys in [62](62-deployment-operations.md). Thesis: **a container is a normal Linux process with its own network namespace — its own interfaces, its own routing table, its own `localhost`, its own port space. Every Docker networking surprise ("it works on my machine", "connection refused", "no such host", "x509: certificate signed by unknown authority") follows from that one sentence plus NAT.**

## Goals
- Build the mental model: **network namespace + veth + bridge + NAT**, and what `-p` actually does.
- Fix the two beginner-killers: **binding to `127.0.0.1` inside a container**, and **`localhost` meaning "this container"**.
- Use **container DNS**: reach other services by **service name** on the **container port**, not the published one.
- Know the network modes (**bridge**, user-defined bridge, **host**, **none**, overlay), `EXPOSE` vs publish, and `host.docker.internal`.
- Handle the Go-specific container issues: the **DNS resolver** choice, missing **CA certs**/`/etc/hosts`/tzdata in `scratch`, health checks with no shell, and PID 1 signals.
- Debug a container's network with no tools inside it, and carry the model to **Kubernetes** (pod IPs, shared netns, Services, cluster DNS).

## Concepts

- **A container is a process with its own network namespace.** Namespaces (net, pid, mnt, uts, ipc) + cgroups = a container. The **net namespace** gives the process its own **interfaces**, **routing table**, **iptables rules**, and **port space** — that's the entire model. Two containers can both listen on `:8080` without conflict, because those are two different port spaces. It is *not* a VM: the kernel is shared, and everything is still ordinary Linux networking.
- **`localhost` inside a container is the container's own loopback.** This is the #1 bug. `127.0.0.1` in container A does **not** reach container B, nor the host, nor a DB on your laptop. Two consequences:
  - **Bind to `0.0.0.0` (i.e. `:8080`), never `127.0.0.1:8080`,** inside a container — otherwise the port is published but the packet arrives on `eth0` and nothing is listening there. Symptom: `curl localhost:8080` on the host gives **`connection reset`/`empty reply`** while the app logs "listening". (`ListenAndServe("localhost:8080", …)` — check this first, always.)
  - To reach another container, use its **service/container name**, not `localhost`.
- **The default bridge, concretely.** Docker creates a bridge (`docker0`) and, per container, a **veth pair**: one end inside the container's namespace (`eth0`, private IP like `172.17.0.3`), one end attached to the bridge. Outbound traffic is **NAT**ed (`MASQUERADE`) to the host's IP — so containers can call out freely. Inbound needs an explicit mapping.
- **`-p 8080:8080` is a DNAT rule, `EXPOSE` is a comment.** Publishing (`-p hostPort:containerPort`, compose `ports:`) installs an iptables **DNAT** rule (or a userland `docker-proxy`) that rewrites traffic arriving on the host port to the container's IP:port. `EXPOSE` in a Dockerfile is **metadata only** — it documents the port and feeds `-P`; it publishes nothing. Two more details: **`-p 127.0.0.1:8080:8080` binds only to host loopback** (do this for databases — plain `-p` on Linux **bypasses `ufw`**, exposing your DB to the internet); and **containers on the same network don't need publishing at all** to talk to each other.
- **User-defined networks give you DNS — and Compose makes one for you.** On a user-defined bridge (any `docker network create`, and the default network of every `docker compose` project) Docker runs an embedded DNS server at **`127.0.0.11`** that resolves **container names, service names, and network aliases** to current container IPs. So from the `api` container: `postgres://db:5432/...`, `http://cache:6379`, `http://worker:8080` — **the container port, not the published one**. The legacy *default* `bridge` network has no DNS (only deprecated `--link`), which is why "it works in compose but not with plain `docker run`" happens. Never hardcode container IPs: they change on every recreate.
- **Compose network semantics in one list.** All services join a project network and are reachable by **service name** (plus `aliases`); `ports:` publishes to the host (only needed for what *you* hit from outside), `expose:` documents; **`depends_on` waits for *start*, not readiness** — pair it with a `healthcheck` + `condition: service_healthy`, and *still* retry in code ([36](36-resilience-patterns.md)) because dependencies restart; `networks:` can split front/back tiers, and an **`internal: true`** network has no egress (a nice blast-radius control for a DB tier); scaling a service (`--scale api=3`) makes the name resolve to **multiple A records** — Go's resolver picks one, so DNS round-robin is your poor-man's load balancer (and long-lived connections stick to whichever IP they got, [63](63-networking-fundamentals.md)).
- **The other network modes.** **`--network host`** puts the container in the *host's* namespace: no isolation, no `-p` needed, `localhost` = the host — the fastest option and the right one for some agents/load tests, **Linux-only** (on Docker Desktop for macOS/Windows a Linux VM sits in between, so "host" is the VM, not your Mac). **`--network none`** = loopback only. **`--network container:<id>`** shares another container's namespace — exactly what a Kubernetes pod does, and the trick for debugging (below). **Overlay** networks span hosts (Swarm/multi-host) and usually carry a **smaller MTU** (~1450) — the classic symptom is "small requests work, TLS handshakes/large POSTs hang".
- **Reaching the host from a container, and vice versa.** Container → host: **`host.docker.internal`** (Docker Desktop; on Linux add `--add-host=host.docker.internal:host-gateway` or use the bridge gateway IP `172.17.0.1`). Host → container: the published port on `localhost`. Container → container: the service name. Write these as **config** ([62](62-deployment-operations.md)) so the same binary runs on a laptop, in compose, and in Kubernetes with only env changes.
- **Go-specific container gotchas.**
  - **DNS resolver:** `CGO_ENABLED=0` builds ([60](60-build-package.md)) always use the **pure-Go resolver**, which reads `/etc/resolv.conf` directly — good, because a `scratch` image has no NSS libraries and the cgo resolver would fail. Docker writes a `resolv.conf` pointing at `127.0.0.11`; `ndots`/`search` domains matter more in Kubernetes (see below). Debug with `GODEBUG=netdns=2`.
  - **Missing root CAs:** a `FROM scratch` image has no `/etc/ssl/certs`, so every outbound HTTPS call fails with **`x509: certificate signed by unknown authority`**. Copy them in (`COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/`) or use **distroless**, which ships them ([60](60-build-package.md)).
  - Also missing in `scratch`: **tzdata** (`time.LoadLocation` fails — or import `_ "time/tzdata"` to embed it), `/etc/passwd` (a numeric `USER 65532` works anyway), and `/etc/hosts` entries.
  - **PID 1:** your Go binary is PID 1, so it gets **SIGTERM directly** (good — [62](62-deployment-operations.md)) but there's no zombie reaper and no shell-based signal forwarding. Use the **exec form** `ENTRYPOINT ["/app"]` (the shell form makes `/bin/sh` PID 1 and swallows signals), and `--init`/tini only if you spawn children.
  - **Health checks with no shell:** `scratch`/distroless have no `curl`/`wget`. Either add a `--healthcheck` **flag to your own binary** (`HEALTHCHECK CMD ["/app", "-healthcheck"]`) or use an orchestrator-level HTTP probe ([62](62-deployment-operations.md)) which needs no in-image client.
  - **`GOMAXPROCS`/`GOMEMLIMIT`** still apply — the runtime sees the *host's* CPUs unless told otherwise ([62](62-deployment-operations.md)).
- **Debugging when the image has no tools.** From the host: `docker network ls`, `docker network inspect <net>` (subnet, gateway, connected containers + IPs), `docker port <ctr>`, `docker inspect -f '{{json .NetworkSettings}}'`, `ss -tulpn` (is the *host* port bound?), `iptables -t nat -L DOCKER`. From *inside* a distroless container, attach a toolbox to its namespace: `docker run --rm -it --network container:<ctr> nicolaka/netshoot` (then `ss`, `dig`, `curl`, `tcpdump` see exactly what the app sees), or `nsenter -t <pid> -n ss -tulpn`. The decision tree: **host port bound? → published to the right container port? → app bound to `0.0.0.0`? → does the name resolve inside the container? → is the target actually listening?**
- **Kubernetes changes three things (and keeps the rest).** Every **pod gets its own IP** — there is **no port mapping**, you talk to `podIP:containerPort` directly. Containers **within** a pod share one network namespace, so **`localhost` *does* work between them** (that's how sidecars work) — and they can't reuse ports. A **Service** is a stable virtual IP + DNS name (`svc.namespace.svc.cluster.local`) load-balancing to ready pods via kube-proxy/iptables/IPVS; `port` (the Service's) vs `targetPort` (the container's) is the mapping that used to be `-p`. **Cluster DNS** with `ndots: 5` means short names trigger several search-domain lookups — use `svc.namespace` or a trailing dot for hot paths. Headless services (`clusterIP: None`) return pod IPs directly (for gRPC/StatefulSets). Details and manifests are in [62](62-deployment-operations.md).

## Exercises
1. Run a Go server bound to `127.0.0.1:8080` in a container with `-p 8080:8080`; watch it fail from the host. Change to `:8080` and watch it work. Explain both.
2. `docker network inspect bridge` and a compose network: find the subnet, gateway, and each container's IP. Then `docker exec` and read `/etc/resolv.conf` and `/etc/hosts`.
3. Two containers on a user-defined network: call one from the other **by service name** with no `ports:` published at all. Then try the same on the default `bridge` network and see DNS fail.
4. Compose: `api` + `db`, `api` reaching `db:5432` (container port) while only `api` publishes a port. Add a `healthcheck` + `depends_on: condition: service_healthy` and prove `depends_on` alone wasn't enough.
5. Publish with `-p 127.0.0.1:5432:5432` vs `-p 5432:5432`; check reachability from another machine on your LAN (this is a real production exposure bug).
6. Compare `--network host`, default bridge, and `--network none` for the same app: what changes about binding, `-p`, and `localhost`?
7. Reach a service running on your host machine from inside a container via `host.docker.internal` (add `--add-host` on Linux).
8. Build `FROM scratch` and make an HTTPS call — get the `x509` error, then fix it by copying CA certs. Repeat for `time.LoadLocation` with `_ "time/tzdata"`.
9. Break DNS on purpose (wrong service name) and read the Go error; then debug it from inside with `--network container:` + netshoot (`dig`, `ss`, `curl`).
10. Use the shell form `ENTRYPOINT /app`, send `docker stop`, and observe SIGTERM never reaching your handler; fix with the exec form and confirm graceful shutdown ([62](62-deployment-operations.md)).
11. Add a `HEALTHCHECK` that runs your binary with a `-healthcheck` flag (no shell, no curl in the image).
12. Capstone: a three-service compose stack (`api`, `worker`, `db`) on **two networks** — a public one for `api` and an `internal: true` back-end network for `db` — with healthchecks, only `api` publishing a port, and a documented "who can reach whom" table you verify with `docker exec`.

## Best Practices & Pitfalls
- **Bind `0.0.0.0` in containers.** Make the address configurable (`HOST`/`ADDR` env) so the same binary can bind loopback behind a local proxy on a VM ([66](66-serving-go-apps.md)).
- **Address other services by name, on the container port.** Never by IP, never via the host's published port, never `localhost`.
- **Publish only what the outside world needs**, and bind sensitive ports to `127.0.0.1` on the host — Docker's iptables rules can sidestep your firewall.
- **`depends_on` ≠ ready.** Use healthchecks *and* retry with backoff in code; dependencies also restart at runtime, when `depends_on` no longer helps at all.
- **Pitfall — `EXPOSE` publishes nothing.** It's documentation. `ports:`/`-p` is the real thing.
- **Pitfall — hardcoded container IPs.** They change on recreate; use DNS names.
- **Pitfall — `scratch` with no CA certs / no tzdata / shell-form ENTRYPOINT.** Three silent, unrelated-looking failures with one root cause: the image is empty by design ([60](60-build-package.md)).
- **Pitfall — assuming Docker Desktop's Linux VM behaves like Linux.** `--network host` and raw bridge IPs behave differently on macOS/Windows; test the real thing in CI ([61](61-ci-github-actions.md)).
- **Pitfall — MTU on overlays/VPNs.** "Handshake hangs, small requests fine" ⇒ set the network MTU, don't chase the app.
- **Carry the config to Kubernetes unchanged.** Same binary, same env vars, different plumbing: pod IP instead of `-p`, Service DNS instead of compose DNS ([62](62-deployment-operations.md)).
